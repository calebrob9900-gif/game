# 04 — Enemy / Bot AI for a Browser FPS

Research + architecture recommendation for believable enemy AI in our Three.js browser
shooter (`shooter.html`, the "NEON BREACH" wave-survival prototype).

**Date:** 2026-06-20 · **Author:** AI programmer (research pass)

---

## TL;DR — Recommended stack

| Concern | Recommendation |
|---|---|
| **Decision architecture** | **Behavior Tree + Blackboard**, with a small **utility scorer** for target/cover/position selection. Keep it data-driven and interruptible. (BT is what Halo 2/3 shipped; utility scoring is what Last of Us / modern shooters lean on.) |
| **Navigation** | **recast-navigation-js** (WASM Recast/Detour) to *generate* the navmesh + run the **Crowd** + **TileCache temporary obstacles**. Optionally **three-pathfinding** if we ship a *static* pre-baked navmesh and want a tiny dependency. |
| **Perception** | Custom, lightweight: layered vision cones (focus/normal/peripheral) + LOS raycast + hearing spheres for gunfire/footsteps → feeds a staged **awareness** model (Unaware → Suspicious → Alert/Combat) with **last-known-position** investigation. |
| **Combat** | Cover selection (squares/points hidden from player LOS), peek-fire, suppression, coordinated flanking via a lightweight **squad blackboard**, retreat/reposition, grenade flush. Difficulty = tunable reaction time + accuracy, never "perfect aim." |
| **AI helper lib** | **Yuka** for steering/FSM/perception/spatial-partitioning *if* we want batteries included; otherwise hand-roll a tiny BT (or `behaviortree.js`) on top of recast-navigation-js. **Pragmatic pick: recast-navigation-js (nav) + hand-rolled BT/utility (decisions). Yuka is the fallback "all-in-one."** |
| **Performance** | Time-slice AI (budget ~3–5 ms/frame), LOD by distance/visibility, spatial partitioning for neighbor queries, shared raycaster, cap planning to a few agents/frame. Target **8–16 active combatants** comfortably at 60 fps; more if most are LOD'd down. |

## 0. Where we are today (baseline in `shooter.html`)

The current enemies are **reactive scripts**, not an AI architecture:

- Movement = straight-line `seek` toward the player (`g.position.addScaledVector(tmp, speed*dt)`), stop at a fixed range. No pathfinding — they'd walk into walls/cover if the arena weren't open.
- Combat = ranged enemies fire on a cooldown when `clearLOS(eye, player)` is true; accuracy scales with wave (`acc = 0.45 + min(0.3, wave*0.02)`).
- Perception = a single LOS raycast against `solids`. No FOV cone, no hearing, no awareness states, no memory/last-known-position.
- No cover-seeking, flanking, suppression, retreat, or squad coordination (the COD comparison doc honestly flags this as the ⚠️ gap: *"direct pursuit + ranged hold; no flanking"*).

So the goal of this doc: a path from "scripted chase" to "believable tactical enemies" that still fits a single-file / lightweight browser build.

## 1. Decision architectures — FSM vs Behavior Tree vs GOAP vs Utility AI

### Finite State Machine (FSM)
States (Idle/Patrol/Chase/Attack/Search/Flee) with explicit transitions. Trivial to build and debug; this is effectively what we have now (implicitly). **Breaks down as behavior count grows** — transitions explode to O(n²) and become a tangled web. Hierarchical FSMs (HFSM) help but still get brittle. Good for *micro* states inside a single behavior (e.g. a reload animation), bad as the top-level brain.

### Behavior Tree (BT)
A tree of **Selectors** (try children until one succeeds — priority/fallback), **Sequences** (run children in order until one fails), **Decorators** (conditions/inverters/cooldowns), and **leaf Tasks** (actions/conditions) that return `success` / `failure` / `running`. Re-ticked each frame, so it's **reactive and interruptible**. A shared **Blackboard** holds state (target, last-known-pos, current cover, etc.).

- **This is the proven AAA shooter choice.** Behavior trees were pioneered by **Damian Isla at Bungie for Halo 2 (2004)** and presented at GDC 2005 ("Handling Complexity in the Halo 2 AI"). Halo's structure is really a behavior **DAG** (a subtree can appear in several places), with decision-making separated from the behaviors themselves, plus a knowledge/perception layer feeding it. Halo 3 extended this (Isla's "Objective System", Dyckhoff's "Decision Making and Knowledge Representation").
- BTs are *far more expressive than FSMs for control flow* and stay maintainable as complexity grows — they're the default in Unreal (BT + Blackboard) and most engines.
- Weakness: pure BTs are "reactive with no look-ahead" — they don't *plan*; you author the tactics.

### GOAP (Goal-Oriented Action Planning)
Give the agent a **goal** (e.g. `KillEnemy`) and a set of **actions**, each with **preconditions** and **effects**. A planner does an **A\* search over world states** to assemble a valid action sequence at runtime. Emergent: every run can produce a different plan.

- **F.E.A.R. (2005, Jeff Orkin)** is the landmark. Famous insight from "Three States and a Plan": the runtime is a tiny **3-state FSM — Goto / Animate / UseSmartObject** — and GOAP just decides *which* of those to do next. The perceived intelligence (flanking, blind-fire, dive-for-cover, "He's flanking!" barks, coordinated suppression) came from action variety + squad coordination + audio, not from a fancy state machine.
- Strength: emergent, dynamic solutions; great when the action space is rich.
- Weakness: **harder to implement/debug and more expensive than BTs** (planning search per replan), and designers can *lose control* over *how* a goal is achieved (if the plan is unfun, you can only tweak goals/costs).

### Utility AI
Score every candidate action/target with a **utility function** (curves over distance, health, ammo, threat, cover quality), pick the highest. No fixed transitions — *any* decision can follow *any* other, so behavior is fluid and self-prioritizing.

- Excellent for **continuous reprioritization** and selection problems: *which* target to shoot, *which* cover point to take, *whether* to push or retreat. **The Last of Us** human enemy AI (Travis McIntosh / Naughty Dog, Game AI Pro) leans heavily on scored evaluation of cover/positions plus a "vague knowledge" awareness state; Part II expanded dynamic flanking and group tactics.
- Weakness: harder to predict/debug; tuning curves is an art; can feel "twitchy" if not damped.

### Verdict for our game
Use a **Behavior Tree as the top-level brain** (predictable, debuggable, the AAA shooter standard) and embed **utility scoring at the decision points** that are really "pick the best of N" problems (target selection, cover selection, push-vs-retreat). This BT+utility hybrid is exactly how modern shooters are built and gives us Halo-style structure with Last-of-Us-style fluid positioning. **Skip GOAP for now** — its emergent planning is overkill for a wave-survival arena and costs us debuggability + CPU we'd rather spend on more agents. Revisit GOAP only if we move to open, objective-driven levels where authoring every tactic by hand becomes painful.

```
Selector (root)
├─ Sequence: [isDead?] → PlayDeath
├─ Sequence: [underHeavyFire? & lowHP?] → RetreatToCover            ← survival first
├─ Sequence: [hasTarget? & inCoverPeekWindow?] → PeekAndFire
├─ Sequence: [hasTarget? & noLOS or exposed?] → MoveToBestCover     ← utility-scored
├─ Sequence: [squadOrder == FLANK] → MoveToFlankPoint              ← squad blackboard
├─ Sequence: [hasTarget? & hasLOS?] → EngageTarget (aim/fire/suppress)
├─ Sequence: [awareness >= SUSPICIOUS] → InvestigateLastKnownPos
└─ Patrol / Idle
```

## 2. Navigation — navmesh & pathfinding on the web

Our enemies must route *around* cover/walls, not slide through them. Three viable approaches:

### A) Navmesh — recommended primary
A navigation mesh is a set of convex polygons covering walkable floor. Pathfinding = A* over polygon adjacency, then a "string-pull"/funnel to get a straight path. Best fit for 3D level geometry and the industry default.

- **recast-navigation-js** — a **WebAssembly port of Recast & Detour** (the same toolkit used across the AAA industry). It does **navmesh construction** (solo or tiled), **pathfinding queries**, a **Crowd** simulation (multi-agent steering + local avoidance), **off-mesh connections** (ladders/jump-pads/teleporters), and **temporary box/cylinder obstacles via TileCache** for semi-dynamic environments. You can **bake the navmesh at runtime** from Three.js geometry (good for procedural arenas like ours) *or* bake offline and import. Ships `@recast-navigation/three` with a `DebugDrawer` to visualize the mesh. v0.43.0 (Sept 2025), actively maintained, TypeScript, browser + Node via `await init()`. *This is the most capable web nav option and the one I recommend.*
  - https://github.com/isaac-mason/recast-navigation-js · docs: https://docs.recast-navigation-js.isaacmason.com/ · npm: https://www.npmjs.com/package/recast-navigation · examples: https://deepwiki.com/isaac-mason/recast-navigation-js/6.3-basic-examples
  - Note: TileCache assumes small tiles (~32–64 units squared) for good perf; needs Vite `optimizeDeps.exclude` config for the WASM.
- **three-pathfinding** (donmccurdy, based on PatrolJS) — A* over a **pre-built** navmesh you author in Blender/Recast and export as glTF/OBJ. Tiny, well-established (~1.4k★), great `clampStep()` for keeping agents on the mesh. **No runtime generation, no dynamic obstacles.** Pairs well with recast-navigation-js (use Recast to *bake* the mesh, three-pathfinding to *query* it) — but recast-navigation-js can query too, so this is mainly a "minimal dependency / static level" option.
  - https://github.com/donmccurdy/three-pathfinding · npm: https://www.npmjs.com/package/three-pathfinding
- **navcat** (also isaac-mason) — newer pure-JS navmesh build/query lib (no WASM). Worth watching as a lighter alternative: https://github.com/isaac-mason/navcat

### B) Waypoint graph
Hand-placed nodes + edges; A* over the graph. Simplest to author, cheap at runtime, and what many older shooters + the F.E.A.R.-era games used (and what Yuka's graph/A* supports). Downside: coarse paths, no "anywhere on the floor" movement, manual maintenance, cover/flank points must be hand-authored.

### C) Grid A* / flow field
Rasterize the floor to a grid, A* (or a flow field if many agents share one goal — the player). Cheap and dead-simple for a flat arena; flow fields are *excellent* when 10+ enemies all path to the same player. Downside: memory/precision tradeoff, awkward on multi-level geometry, "blocky" paths need smoothing.

### Verdict
Our arena has box "cover" pillars and walls → **navmesh via recast-navigation-js** is the right primary: bake from the arena geometry at load, register cover pillars as **TileCache temporary obstacles** so paths route around them, use the **Crowd** for built-in agent separation/local avoidance (solves the "enemies clumping into one blob" problem the current code has). **Off-mesh links** are ready if we add verticality (jump-downs, vents).

Pragmatic fallback for a truly tiny single-file build: a **grid A* + flow field to the player** (no library), or **three-pathfinding** with one pre-baked arena navmesh. Recommendation order: **recast-navigation-js → flow-field grid → three-pathfinding**.

Sources: recast-navigation-js GitHub/docs/npm (above); three-pathfinding GitHub/npm (above); navcat (above).

## 3. Perception — senses, awareness, memory

Believability comes more from *how/when enemies notice you* than from how they shoot. Build a small sensory system feeding a staged awareness model. The canonical design references are **Thief: The Dark Project's sensory system** and modern view-cone models.

### Vision (layered cones + LOS)
- **Multiple view cones**, not one: **focus** (narrow, long range — what they're looking straight at), **normal** (medium FOV/range), **peripheral** (wide, short range — catches close movement). You're spotted faster when centered & near; sneaking wide/far buys time. (This layered-cone model is standard in modern bot AI.)
- Each potential target inside a cone gets a **LOS raycast** from the eye position to confirm no `solid` blocks it (we already have `clearLOS()` — reuse it, but cast to eye height and a few body points, not just the root).
- Modulate detection by **distance, angle from center, target speed/crouch, and lighting** (Thief weighted visibility by how lit the player was — relevant if we add dark areas).

### Hearing
- Model sounds as **spheres**: gunshots = large radius, footsteps = small (scaled by sprint/crouch), explosions = huge. Loudness falls off with distance from the source. Any agent within radius "hears" it and records the **heard location**. (Directly maps to our existing SFX events — gunfire, steps, grenades — so we get hearing almost for free.)

### Awareness / alert states (staged escalation)
A small per-agent state, raised by sensory stimuli and decaying over time:

```
UNAWARE → SUSPICIOUS → ALERT/SEARCH → COMBAT
   ▲           │ (noise / glimpse)        │ (clear LOS / shot at)
   └───────────┴── decay over time ───────┘ (lost target for N sec)
```

- **UNAWARE**: patrol/idle.
- **SUSPICIOUS** ("vague knowledge", the in-between state Naughty Dog added to TLOU): heard/half-saw something → turn toward it, slow, investigate. Not yet shooting.
- **ALERT/SEARCH**: confirmed something → move to **last-known-position (LKP)**, search nearby, call it out.
- **COMBAT**: has the target → engage (hand off to combat BT).
- Decay: losing LOS doesn't instantly drop to UNAWARE — keep a timer, hold COMBAT briefly, then SEARCH the LKP, then give up. "Is successfully sensed" boolean flips drive acquire/lose transitions.

### Memory / Last-Known-Position
Store on the blackboard: last seen position, last seen velocity (extrapolate where they ran), time since last seen. Enemies push to the LKP and "clear" it, then fan out — this single feature is the biggest believability win over our current "instant forget when LOS breaks."

## 4. Combat behaviors

These are the BT leaf tasks / utility-scored choices that make fights feel tactical.

### Cover (the foundation)
- **Cover point selection** = utility scoring over candidate points: high score if the point **breaks the player's LOS** to the agent, is **near** the agent, **toward** the objective, and **not already taken** by a squadmate. Halo's trick: treat the area as a grid of squares and pick squares *not in the player's line of sight*, then path square-to-square. We can generate cover candidates from the **edges of our box pillars** (left/right/back faces relative to the player).
- **Peek-fire loop**: rise/lean out → short burst → drop back behind cover on a randomized timer. Avoids the "statue trading shots in the open" look the current enemies have.

### Flanking & squad coordination
- A lightweight **squad blackboard / coordinator**: the moment *one* member sees the player, the whole squad learns the position (shared knowledge — no need for every bot to have LOS). The coordinator assigns **roles**: some **hold + suppress** from the front while others are told to **MoveToFlankPoint** around the side → crossfire instead of a conga line.
- **Bounding overwatch / fire-and-movement**: half advance while half lay covering fire, then swap. Even a simplified version (one pusher at a time, rest suppress) reads as smart.
- **Formation spacing**: keep ~6–8 units between members so one grenade can't wipe the squad and they don't merge into a blob (the Crowd's separation handles much of this).

### Suppression
- When the agent lacks a clean shot or wants to pin the player, **fire toward the player's LKP / cover** at reduced accuracy. Effect on the player can be cosmetic (tracers + near-misses) plus a "you're being suppressed" pressure cue. It's cheap and massively raises perceived intelligence (this is core to the F.E.A.R. illusion).

### Retreat / reposition
- On low HP, heavy incoming fire, or losing a position duel → **RetreatToCover** (utility: a cover point *away* from the player, ideally with squad support). Put survival high in the BT so it preempts engaging.

### Grenades
- **Flush behavior**: if the player has been static behind cover for N seconds and is in throw range with a valid arc, lob a grenade to force them out. We already have a full grenade arc/physics + AoE system for the player — reuse it for enemies. Gate by cooldown + line-of-arc check so they don't spam.

### Difficulty scaling (do it *fairly*)
- **Never give bots perfect aim or zero reaction time** — that's the #1 thing that makes AI feel cheap/unfair (see the Ravenfield "even Easy has perfect aim" complaint). Scale these instead:
  - **Reaction time**: delay between acquiring LOS and first shot (e.g. 600 ms easy → 200 ms hard).
  - **Aim error**: an angular spread cone around the true direction, tightening with difficulty and *converging over time on target* (so they "walk" fire onto you rather than headshot instantly). Add deliberate first-shot inaccuracy.
  - **Engagement aggression**: how often they push/flank/grenade.
  - **Burst discipline**: trigger control, time between bursts.
- Our current `acc = 0.45 + min(0.3, wave*0.02)` is a start; replace the binary hit-roll with an **aim-cone + convergence** model so misses look like spray, not dice.

### Recommended stack (two valid paths)

**Path A — "Best of breed" (recommended for the big build):**
- **recast-navigation-js** for navmesh + Crowd + dynamic obstacles.
- **Hand-rolled (or `behaviortree.js`) Behavior Tree + Blackboard** for decisions.
- **Small utility scorer** for target/cover/push-retreat selection.
- **Custom perception** (cones + LOS + hearing + awareness/LKP) — reuse our existing `clearLOS`/SFX events.

**Path B — "All-in-one" (fastest to a believable demo):**
- **Yuka** for steering + FSM/goal agents + perception + navmesh A* + spatial partitioning, with **Three.js** purely as the renderer (sync Yuka entity transforms → Three.js objects each frame).
- Add a thin BT/utility layer on top only where Yuka's FSM/goal model isn't expressive enough.

**My pick:** Start the *prototype upgrade* with **Yuka** (Path B) to get layered perception + navmesh movement + steering separation working fast against the existing arena, then migrate navigation to **recast-navigation-js** (Path A) for the big build when we need runtime-baked navmeshes and dynamic-obstacle cover. Keep decisions in our own BT+utility either way so we own the tactics.

## 6. Performance — how many agents at 60 fps

### The budget
60 fps = **~16.7 ms/frame total**, shared with rendering, physics, post-FX (we already run UnrealBloom). A common pattern is to reserve a **strict JS slice (~5 ms)** for logic and bail out when exceeded. Treat AI as a **3–5 ms/frame budget** and time-slice within it.

### Techniques (apply roughly in this order of payoff)
1. **Don't run everything every frame.** Tick expensive AI (perception raycasts, pathfinding, BT re-evaluation) at **5–10 Hz**, not 60 — stagger agents across frames (agent `i` updates on `frame % N == i % N`). Movement/steering can still update at 60.
2. **LOD for AI** (LOD applied to *behavior*, not just meshes): full simulation for near/visible/in-combat agents; reduced (slower tick, no fine steering, no peek micro-behavior) for mid; near-frozen "fake" sim for far/off-screen. Detail scales with camera distance — the standard LOD-AI approach.
3. **Spatial partitioning** for neighbor/perception queries (who can I see/hear, who's my squad nearby) — a uniform grid / cell-space partitioning turns O(n²) into near O(n). Yuka ships `CellSpacePartitioning`; recast's Crowd handles neighbor avoidance internally. Measured impact in the wild: spatial partitioning held 60 fps in **92% of sessions vs 67%** unoptimized.
4. **Cap heavy work per frame**: e.g. at most **1–2 path re-plans per frame** (queue the rest), one LOS raycast batch per agent per AI-tick. Share a single `Raycaster` (we already do) and cache LOS results within a tick.
5. **Object pooling**: reuse enemy/tracer/particle objects (we partly do via the `corpses` reuse) to avoid GC hitches.
6. **Avoid per-frame allocations** in the AI loop (reuse Vector3 scratch objects — the code already uses a `tmp` vector; extend that discipline).

### Realistic numbers for our browser FPS
- With **per-frame straight-line scripts** (today) you can have *many* enemies, but they're dumb.
- With a **full BT + perception + navmesh** per agent at 60 Hz, expect to comfortably run **~8–16 active combatants** at 60 fps on a mid laptop — which matches a CoD/wave-survival firefight (our `maxAlive` is currently 9, so this is right in range).
- With **time-slicing + AI LOD**, push to **30–50+** total agents if only ~8–12 are "hot" (near/visible/in-combat) at any moment and the rest are LOD'd down.
- The WASM Recast **Crowd** is built for many agents and offloads steering/avoidance efficiently; planning (A* path queries) is the thing to throttle/queue.

## 7. Proposed architecture for our game (concrete)

Target: upgrade `shooter.html`'s wave-survival enemies from "scripted chase" to "tactical squads," in a way that fits the lightweight browser build.

### Data model (per enemy + shared)
- **Blackboard (per agent):** `self`, `target`, `awareness` (UNAWARE/SUSPICIOUS/ALERT/COMBAT), `lastKnownPos`, `lastSeenVel`, `timeSinceSeen`, `currentCover`, `squadOrder` (HOLD/SUPPRESS/FLANK_L/FLANK_R/RETREAT), `hp`, `ammo`, `peekTimer`.
- **Squad coordinator (one per active wave):** shared `playerKnownPos` (set when *any* member sees player), role assignment, push-token (only K pushers/flankers at once), grenade-cooldown gate.

### Systems & tick rates
- **Perception (10 Hz, staggered):** for each agent, run layered cone test + `clearLOS` (reuse existing) to eye/body points; feed hearing from SFX events (shots/steps/grenades) as sound spheres; update awareness + LKP. On first sight, push player pos to squad coordinator.
- **Navigation (recast-navigation-js, or grid flow-field fallback):** bake arena navmesh at load; register cover pillars as TileCache obstacles; use **Crowd** for movement + separation. Replan path on goal change only, ≤2 replans/frame (queue rest).
- **Decision (BT + utility, 5–10 Hz):** tick the BT in §1; utility-score cover points (LOS-breaking + near + role) and targets; choose peek/suppress/flank/retreat.
- **Combat (60 Hz for aim/fire feel):** aim-cone + convergence model (fair difficulty), peek-fire loop, suppression toward LKP, enemy grenade flush reusing the existing arc system.
- **Movement/animation (60 Hz):** drive existing GLTF mixer; sync Crowd/steering position to the Three.js group.

### Performance plan
- AI LOD: hot agents (visible/in-combat) full sim; others slow-tick + simplified. Time-slice perception/planning across frames; cap re-plans; reuse scratch vectors + single raycaster. Keep `maxAlive` ~9–12 hot; allow more total via LOD.

### Incremental rollout (lowest risk → highest value)
1. **Awareness + LKP + investigate** on top of current movement (no nav lib yet) — biggest believability jump for least code.
2. **Cover selection + peek-fire** using pillar-edge candidate points + existing `clearLOS`.
3. **Navmesh routing** (recast-navigation-js Crowd) so they path around cover and don't clump.
4. **Squad coordinator**: shared knowledge, flank role assignment, suppression.
5. **Fair difficulty model** (aim-cone + reaction-time) + **grenade flush** + **retreat**.
6. **AI LOD + time-slicing** once agent counts climb.

This lands us at "F.E.A.R./Halo-flavored" tactical enemies — flanking, suppressing, taking cover, investigating your last position — while staying inside a browser frame budget.
